# SevynOS Architecture v0.1

**Codename:** Genesis
**Organization:** Project Sevyn
**Status:** Draft
**Version:** 0.1

## 1. Purpose

SevynOS is an open, cross-device operating system platform built on the Linux kernel, with TypeScript and React Native as first-class development technologies.

The purpose of SevynOS is to create a computing platform that combines:

- user ownership
- developer freedom
- cross-device consistency
- modern application development
- high performance
- a simple and polished user experience

SevynOS is intended to eventually support phones, desktops, tablets, watches, televisions, embedded systems, and other computing devices through a shared runtime, SDK, application model, and design language.

This document describes the first proposed architecture for SevynOS. It is an early blueprint and is expected to evolve as the platform is prototyped, tested, and better understood.

---

## 2. Core Architectural Goal

The first technical goal of SevynOS is:

> Run a React Native application inside a desktop environment controlled by SevynOS.

This prototype does not need to be a complete operating system.

It must prove that SevynOS can provide its own application environment, system APIs, lifecycle model, and user interface while using Linux as the underlying system foundation.

The first prototype should demonstrate:

- a SevynOS desktop shell
- an application launcher
- basic window management
- application lifecycle management
- a small SevynOS SDK
- at least one React Native application
- communication between TypeScript and native system services

## 3. Architectural Principles

### 3.1 Linux is the foundation, not the product

SevynOS will use the Linux kernel for low-level responsibilities such as:

- process scheduling
- memory management
- hardware drivers
- networking
- storage
- device communication
- security primitives

SevynOS will not attempt to replace or rewrite the Linux kernel.

The Linux foundation should remain mostly invisible to application developers and ordinary users. Developers should build against SevynOS APIs rather than directly depending on Linux-specific interfaces.

### 3.2 TypeScript first

TypeScript should be used wherever it can perform the required work reliably and efficiently.

Likely TypeScript components include:

- the shell interface
- system applications
- developer tooling
- command-line tools
- application APIs
- SDK packages
- configuration systems
- package metadata
- application lifecycle coordination

Native code should be introduced only where required for:

- operating-system integration
- performance-sensitive operations
- hardware access
- graphics integration
- process control
- security boundaries
- React Native platform bindings

### 3.3 React Native is a first-class platform

SevynOS should not merely run React Native applications through an emulator or compatibility layer.

The long-term goal is for React Native to recognize SevynOS as a platform target in the same general way it recognizes Android, iOS, Windows, and macOS.

A future application should be able to detect the platform using an interface such as:

```ts
Platform.OS === "sevynos";
```

Existing React Native applications should require as few changes as reasonably possible to run on SevynOS.

### 3.4 System applications must use the public platform

Whenever practical, SevynOS system applications should use the same SDK and application model available to third-party developers.

Examples include:

- Settings
- Files
- Terminal
- App Manager
- Notifications
- Launcher
- Calculator
- Media applications

This prevents SevynOS from offering internal capabilities that outside developers cannot access without a clear security reason.

### 3.5 Openness with defined boundaries

SevynOS should be open by default, but openness does not mean the absence of architecture, security, permissions, or project governance.

The platform should provide:

- documented APIs
- replaceable system applications
- user-controlled developer access
- open package formats
- transparent permissions
- clear contribution standards
- stable compatibility guarantees

## 5. Major Platform Components

### 5.1 Linux Kernel

The Linux kernel provides the low-level operating-system foundation.

SevynOS should initially use an existing Linux distribution or minimal Linux system during development rather than immediately producing a complete custom image.

This allows the project to focus first on the differentiating platform layers.

The development foundation may change later as requirements become clearer.

### 5.2 System Services

System services expose controlled access to operating-system capabilities.

Possible services include:

- display service
- input service
- audio service
- network service
- storage service
- notification service
- permission service
- device service
- power service
- session service
- application service

These services should communicate through defined interfaces rather than allowing every application to directly access low-level Linux resources.

### 5.3 Sevyn Runtime

The Sevyn Runtime is the central application-management layer of the platform.

Its responsibilities may include:

- discovering installed applications
- validating application manifests
- launching applications
- stopping applications
- tracking application state
- managing foreground and background behavior
- enforcing permissions
- routing system events
- managing inter-process communication
- maintaining the application registry
- exposing system capabilities to the SDK

The Runtime should be designed independently from the visual shell.

This separation allows different SevynOS device categories to use different shells while sharing the same application model.

### 5.4 React Native Platform Layer

The React Native platform layer allows React Native applications to run as SevynOS applications.

Its responsibilities may include:

- hosting the React Native runtime
- implementing SevynOS native components
- exposing native modules
- translating input events
- connecting applications to the graphics system
- integrating with the application lifecycle
- providing SevynOS platform constants
- supporting development and debugging tools

The initial prototype may use an existing React Native desktop implementation as a research base, but SevynOS should avoid becoming permanently dependent on assumptions belonging to another platform.

### 5.5 SevynOS SDK

The SDK is the primary interface used by application developers.

Example:

```ts
import { App, Files, Notifications, Permissions, Storage, Windows } from "@sevynos/sdk";
```

The SDK should provide stable, documented TypeScript APIs.

Early SDK modules may include:

```text
@sevynos/app
@sevynos/files
@sevynos/notifications
@sevynos/permissions
@sevynos/storage
@sevynos/system
@sevynos/windows
```

The SDK should hide unnecessary native and Linux-specific details from developers.

### 5.6 Sevyn Shell

The Sevyn Shell is the primary user-facing system interface.

The desktop prototype may include:

- desktop workspace
- application launcher
- taskbar or dock
- window chrome
- application switcher
- notification center
- quick settings
- system status indicators
- lock screen
- session controls

The shell should be written primarily with TypeScript and React Native.

The Shell must communicate with the Runtime through public, documented interfaces.

### 5.7 Applications

SevynOS applications should be packaged units containing:

- application code
- assets
- metadata
- permissions
- entry points
- supported device categories
- version information
- developer identity
- optional native extensions

A possible application manifest could resemble:

```json
{
  "id": "com.projectsevyn.settings",
  "name": "Settings",
  "version": "0.1.0",
  "entry": "./src/index.tsx",
  "platform": "sevynos",
  "permissions": ["system.settings.read", "system.settings.write"],
  "devices": ["desktop"]
}
```

The exact manifest format has not yet been selected.

## 6. Application Lifecycle

The initial application lifecycle may contain the following states:

```text
Installed
   │
   ▼
Starting
   │
   ▼
Running
   │
   ├──► Background
   │         │
   │         └──► Running
   │
   ├──► Suspended
   │
   └──► Stopping
             │
             ▼
           Stopped
```

The Runtime should own application lifecycle state.

Applications should receive lifecycle events through the SDK.

Example:

```ts
import { AppLifecycle } from "@sevynos/app";

AppLifecycle.on("background", () => {
  console.log("Application moved to background.");
});

AppLifecycle.on("foreground", () => {
  console.log("Application returned to foreground.");
});
```

Desktop, mobile, watch, and embedded devices may apply different lifecycle policies while preserving a shared application interface.

## 7. Security and Permissions

Applications should not automatically receive unrestricted access to the system.

SevynOS must balance user ownership with meaningful security boundaries.

Possible permission categories include:

- camera
- microphone
- location
- contacts
- notifications
- files
- network
- Bluetooth
- background execution
- system settings
- device information

Users should be able to inspect, grant, deny, and revoke permissions.

Developer Mode may allow advanced access, but it must clearly explain the security consequences of enabling additional capabilities.

User ownership means the user can deliberately remove restrictions from their own device. It does not mean every installed application should automatically receive unrestricted access.

## 8. Cross-Device Design

SevynOS should use one shared platform architecture while allowing device-specific experiences.

```text
                   Sevyn Runtime
                         │
       ┌─────────────────┼─────────────────┐
       │                 │                 │
 Desktop Shell      Mobile Shell      Watch Shell
       │                 │                 │
 Desktop APIs       Mobile APIs       Watch APIs
```

Shared capabilities should use common APIs.

Device-specific capabilities should use capability detection rather than hard-coded assumptions.

Example:

```ts
import { Device } from "@sevynos/system";

if (Device.hasCapability("camera")) {
  // Enable camera functionality.
}
```

This is preferable to assuming that every phone, desktop, watch, or television has the same hardware.

## 9. Initial Technology Direction

The following technologies are currently proposed, not permanently selected:

| Layer                        | Proposed Direction                                 |
| ---------------------------- | -------------------------------------------------- |
| Kernel                       | Linux                                              |
| Primary application language | TypeScript                                         |
| System interface framework   | React Native                                       |
| Native integration           | C++ and possibly Rust                              |
| JavaScript engine            | Hermes                                             |
| Source control               | Git                                                |
| Repository model             | Monorepo                                           |
| Documentation                | Markdown                                           |
| Build tooling                | To be determined                                   |
| Graphics and compositor      | To be researched                                   |
| Display protocol             | Wayland is a leading candidate                     |
| Inter-process communication  | To be determined                                   |
| Package format               | Custom format or existing standard to be evaluated |

Every major selection must eventually receive an Architecture Decision Record.

## 11. Version 0.1 Prototype Scope

Version 0.1 should remain intentionally small.

### Included

- desktop development environment
- one Linux target
- basic shell process
- application launcher
- simple window representation
- application registry
- application manifest
- one React Native application
- basic lifecycle events
- one or two SDK modules
- development logging
- documented startup process

### Not included

- custom phone hardware
- cellular connectivity
- production security model
- complete package manager
- public application store
- full mobile shell
- watch support
- television support
- custom Linux kernel
- complete driver stack
- cloud synchronization
- commercial deployment

The purpose of Version 0.1 is validation, not completeness.

## 12. Definition of Success

Architecture v0.1 will be considered successfully validated when:

1. A Linux development environment launches the Sevyn Shell.
2. The Shell displays an application launcher.
3. The launcher discovers an installed application from a manifest.
4. The Runtime starts the application.
5. The application renders through React Native.
6. The application receives at least one lifecycle event.
7. The application calls at least one SevynOS SDK API.
8. The application closes cleanly through the Runtime.

The ideal demonstration is:

> An existing simple React Native application can be adapted to run on SevynOS with minimal application-level changes.

## 13. Open Questions

The following questions must be researched before the architecture is finalized:

1. Should the first prototype use React Native Windows, React Native macOS, React Native Skia, or a custom Linux renderer as its starting point?
2. Which compositor and window-management strategy should SevynOS use?
3. Should the Runtime be a single process or a collection of services?
4. Which IPC mechanism should connect applications, services, and the Runtime?
5. Should native SevynOS components be implemented using C++, Rust, or a combination?
6. How should application isolation work?
7. How should native extensions be packaged?
8. How closely should the application manifest resemble existing React Native or web standards?
9. Which parts of the React Native platform must be implemented for the first prototype?
10. How will developer hot reload and debugging work?
11. How should SevynOS represent device capabilities?
12. What compatibility guarantees will the SDK provide?

Each resolved question should produce an Architecture Decision Record.

## 15. Closing Statement

SevynOS will not attempt to reinvent every layer of modern computing.

It will build upon proven open technologies while creating a new application platform centered on user ownership, developer freedom, TypeScript, React Native, and cross-device consistency.

Architecture v0.1 is not a final specification.

It is the first technical map for turning the SevynOS vision into a working platform.
